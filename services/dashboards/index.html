Dashboards and BI for operations teams · Data pipeline and reconciliation

Still building Monday’s report from four CSV exports, with totals that never match?

  1. Platform data into SQL Server, reconciled every night

    Shopify, ShipHero, HubSpot, Xero or QuickBooks pulled by API into staging tables each night, your ERP from its scheduled export, then stored procedures building silver and fact tables. Every transformation is inspectable in SQL.

    Where a person decides: Your finance or QC team signs off the parity audit column by column before the old report is switched off.

    Data systemsComplex system · multi-week
  2. Root causes of inflated totals found and handled

    Voided shipments, duplicate rows and refunds that inflate totals are traced to their cause and handled explicitly in the pipeline, not filtered by hand.

    Where a person decides: Each handling rule is agreed with you before it is applied.

    Data systemsStandard build · 2–6 weeks
  3. CSV exports loaded into SQL on arrival

    The CSV exports from Shopify, Xero, HubSpot or Zendesk land in a shared folder or inbox and are loaded into one SQL table on arrival, with row counts and totals checked against the file.

    Where a person decides: A file that fails its checks is held, not loaded. You see a load log per file.

    Data systemsQuick win · days to 2 weeks
  4. Incremental loads with change tracking

    Only new and changed rows are pulled on each run, with watermarks per source and a full reload path, so the nightly sync stays fast as volume grows and a bad run can be replayed.

    Where a person decides: You choose the run schedule and when a full reload is allowed to run.

    Data systemsStandard build · 2–6 weeks
  5. Currency, time zone and unit normalisation

    Orders in several currencies, time stamps in several zones, and weights, pack sizes and case quantities that differ by platform are normalised once in the silver layer, with the original values kept beside the converted ones.

    Where a person decides: You set the reporting currency, time zone and rate source; conversions are never silent.

    Data systemsStandard build · 2–6 weeks

Closest system I’ve shipped: E-commerce Fulfillment ETL. This is the niche, already built: 68,890 orders reconciled across 25 audited columns, nightly, for a US retailer’s finance team.

Dashboards and BI for operations teams · Legacy reports and cutover

Still running the old report next to the new one because nobody trusts either?

  1. Column-by-column parity audit against the legacy report

    The new fact tables are compared with the legacy system’s output row by row and column by column, not sampled. Every difference is listed with its cause and a proposed handling rule.

    Where a person decides: Your team signs off each column. Cutover does not happen until the sign-off is complete.

    Data systemsStandard build · 2–6 weeks
  2. Legacy database migrated into SQL Server

    Access databases, old SQL instances, Airtable bases or a retiring ERP’s export are migrated into SQL Server with history preserved and keys mapped. Old and new run in parallel until the parity audit passes.

    Where a person decides: You decide the cutover date; the old system stays readable until you say otherwise.

    Data systemsComplex system · multi-week
  3. Historical backfill from exports and archives

    Years of CSV exports, archived spreadsheets and old database dumps loaded into the same tables with the same checks, so the dashboard has history on day one rather than starting from zero.

    Where a person decides: You choose how far back to load and which periods are allowed to differ.

    Data systemsStandard build · 2–6 weeks
  4. Old report rebuilt, matched, then retired

    The report someone runs by hand every Monday is rebuilt as a scheduled query on the new tables, matched against the last three manual versions, and only then taken over.

    Where a person decides: The report owner approves the switch; the manual version is archived, not deleted.

    Data systemsQuick win · days to 2 weeks
  5. Reference data and key mapping tables

    Customer IDs, SKU codes and account names that differ between the old and new systems are mapped once in a table your team can edit, so joins stop depending on someone’s memory.

    Where a person decides: Your team owns the mapping table; unmapped keys are listed, never guessed.

    Data systemsQuick win · days to 2 weeks

Closest system I’ve shipped: E-commerce Fulfillment ETL. That retailer’s cutover was audited this way: 68,890 orders, 25 columns, alongside the client’s QC team. A US retailer, not a BI team.

Still rebuilding the month-end pack by hand from exports, the week after close?

  1. Month-end pack built and sent on schedule

    The pivot tables and exports someone assembles every month become a scheduled job that builds the pack from the fact tables as Excel and PDF and sends it before the meeting, every figure linked to its source.

    Where a person decides: The controller reads and signs off. The job never posts an adjustment.

    AutomationStandard build · 2–6 weeks
  2. Variance commentary drafted next to the numbers

    A model reads this month’s figures against last month and budget and drafts the variance notes in your pack’s wording, each sentence tied to the rows behind it. Where the data shows no cause, it says so.

    AI systemsStandard build · 2–6 weeks
  3. Weekly team reports, one per manager

    Each site, team or client manager gets their own slice of the same report on a schedule, by email, Slack or Teams, built from one query so the numbers cannot drift apart.

    Where a person decides: You decide who gets what; the first send to each person is reviewed by you.

    AutomationQuick win · days to 2 weeks
  4. Ad hoc data requests become saved queries

    The “can you pull me the numbers for” requests that interrupt your analyst become saved, parameterised queries run from a short form or a Slack command, delivered as Excel with the SQL shown. A request nobody has saved yet still goes to a person.

    Where a person decides: The analyst approves each saved query once; after that it runs for whoever you allow.

    AutomationQuick win · days to 2 weeks

Dashboards and BI for operations teams · Data quality and alerts

Still finding out a sync broke when the dashboard looks wrong days later?

  1. Freshness and row-count checks on every load

    Each table carries its last-loaded time and expected row range. A load that is late, empty or far from the usual volume is flagged in Slack or Teams the same morning.

    Where a person decides: A person decides whether to rerun or wait; the check only alerts.

    Data systemsQuick win · days to 2 weeks
  2. Expired tokens and stalled connections caught early

    API tokens, OAuth grants and SFTP logins to each platform are tested on schedule, with non-expiring auth flows where the platform allows it, so the sync does not silently stop after a refresh.

    Where a person decides: A person reconnects the platform; the system only alerts.

    AutomationQuick win · days to 2 weeks
  3. Bad rows quarantined with the reason

    Deterministic checks on every row: required fields, valid dates, totals that add up, keys that exist. Rows that fail are held in a quarantine table with the failed rule, and the rest load.

    Where a person decides: Your team clears the quarantine; a rule is never relaxed without your sign-off.

    Data systemsStandard build · 2–6 weeks
  4. Numbers out of range flagged before sending

    A total that moves more than its usual range day on day, a customer that appears twice, a negative stock figure: flagged with the rows behind it before the report goes out.

    Where a person decides: You choose which flags hold the report and which only annotate it.

    Data systemsStandard build · 2–6 weeks
  5. Data quality scorecard per source

    A Power BI page showing, per platform, when it last loaded, how many rows failed which rule, and how long the quarantine has been open. Built on the freshness and quarantine tables above.

    Where a person decides: The data owner decides what to fix first.

    Data systemsQuick win · days to 2 weeks
  6. Closed periods still reproduce after changes

    Customer, SKU and price dimensions keep their history, and every stored procedure has a regression test over a frozen month, so a report rerun for a closed period returns the same figures after a change to the pipeline.

    Where a person decides: A failed test blocks the release until you accept the new figures in writing.

    Data systemsStandard build · 2–6 weeks

Closest system I’ve shipped: E-commerce Fulfillment ETL. Root-cause debugging in that retailer’s pipeline found voided shipments and multi-cause inflation; these checks come from that. A US retailer’s finance team, not BI.

Still leaving the paperwork out of the numbers because it only exists as scans?

  1. Invoices and scans extracted into the dataset

    Supplier invoices, delivery notes, scanned PDFs and HTML exports extracted by text and vision models into the same validated tables, with deterministic checks after the model.

    Where a person decides: Nothing is written until it passes the gate. A person clears the queue; the pipeline never guesses.

    AI systemsComplex system · multi-week
  2. Entity resolution built for OCR noise

    “ACME Ltd” and “Acme Limited” resolved to one supplier with an escalating matcher instead of one similarity threshold.

    Where a person decides: Low-confidence matches are confirmed by a person once, then remembered.

    AI systemsStandard build · 2–6 weeks
  3. Inbox and shared-drive intake for documents

    Attachments arriving in a shared mailbox, a SharePoint or Google Drive folder, or a Dropbox upload are picked up on arrival by n8n, deduplicated and handed to the extraction pipeline with their source recorded.

    Where a person decides: You choose the folders and mailboxes; nothing is moved or deleted at source.

    AutomationQuick win · days to 2 weeks
  4. Documents matched to orders and payments

    Each extracted invoice or delivery note is joined to the order, shipment and payment it belongs to in the fact tables, so cost per order and unmatched paperwork become queries, not a hunt.

    Where a person decides: Unmatched documents are listed for a person; nothing is force-matched.

    Data systemsStandard build · 2–6 weeks
  5. Exceptions queue with the failed rule shown

    A small web screen built on Next.js and FastAPI: the scan on the left, the extracted fields and the rule it failed on the right. Staff correct, resubmit, and the correction is logged.

    Where a person decides: Only a person can override a failed rule, and the override is recorded with their name.

    AI productsStandard build · 2–6 weeks

Closest system I’ve shipped: Tournament Document Intelligence. 412 records, 0 validation errors with an 8-tier fuzzy resolver and a hard validation gate. Tournament data, not operations paperwork.

Still running operations from one master spreadsheet that only one person understands?

  1. Sheet formulas rebuilt as SQL, then matched

    The lookups, pivots and formulas in the master workbook are mapped and rebuilt as stored procedures over the same inputs, then run beside the sheet until both agree, tab by tab.

    Where a person decides: The sheet’s owner signs off each tab. The workbook is not retired until they do.

    Data systemsComplex system · multi-week
  2. Excel stays, but it reads the database

    The workbooks people will not give up are connected to the SQL views with refreshable Power Query connections, so the formulas stay, the pasted-in data goes, and a refresh replaces the retyping.

    Where a person decides: The workbook owner keeps the workbook; only the data tabs change.

    Data systemsQuick win · days to 2 weeks
  3. Manual inputs through a form, not cells

    The handful of numbers someone types in each week, targets, headcount, adjustments, are entered through a short form that writes to a table with validation and a who-and-when stamp.

    Where a person decides: You decide who may enter which figures; every entry is traceable to a person.

    AutomationQuick win · days to 2 weeks
  4. Google Sheets and Airtable as governed sources

    The Sheets and Airtable bases teams already fill in are read into staging on schedule by API, with locked columns, type checks and a change log, so they become inputs to the pipeline rather than the pipeline itself.

    Where a person decides: Sheet owners keep editing rights; a row that fails a type check is flagged, not dropped.

    Data systemsStandard build · 2–6 weeks
  5. Macros and VBA replaced by scheduled jobs

    The VBA macros and manual refresh buttons that only run on one laptop become scheduled jobs on a server, logged, with the same outputs and an alert when a run fails.

    Where a person decides: The macro’s author checks the first runs against the old output.

    AutomationStandard build · 2–6 weeks

Closest system I’ve shipped: E-commerce Fulfillment ETL. Staging and stored procedures, every transformation inspectable in SQL, parity-audited before cutover. The legacy there was a retailer’s system, not a spreadsheet.

    Data systemsComplex system · multi-week
  2. Self-hosted models for documents that cannot leave

    Open-weight text and vision models run on your own GPU server for the extraction steps, so invoices, contracts and personal data in the pipeline never reach a third-party API. Extraction accuracy on your documents is measured before cutover.

    Where a person decides: You decide which document types may use a hosted API and which may not.

    AI productsComplex system · multi-week
  3. Who can see what, written down and enforced

    Database roles, Power BI workspaces and row-level security mapped to your Microsoft 365 or Google groups, reviewed with you, and exported as a list security can read.

    Where a person decides: Your admin grants and removes access; I document and check it.

    Data systemsQuick win · days to 2 weeks
  4. Backups, restore drills and a runbook
