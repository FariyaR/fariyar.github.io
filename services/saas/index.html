SaaS and software companies · Slow inference in production

Still shipping an AI feature that works in the demo and times out in production?

  1. Queued jobs and polling instead of held requests

    A FastAPI job API and a GPU worker as separate services: jobs are queued and polled, not held open until they time out, and the expensive part scales on its own. Your Next.js app shows progress.

    Where a person decides: Every job is tracked from upload to result with status and timing, so your team can audit a run.

    AI productsComplex system · multi-week
  2. Self-hosted models where data must stay

    Open-weight models on your own GPUs, on RunPod or a hardened EU-resident server, served by the same job API and worker, so an enterprise security review does not stall on a third-party API.

    Where a person decides: You sign off the architecture sketch before the build starts.

    AI productsComplex system · multi-week
  3. Typed contracts on every boundary

    Model output validated into a fixed Pydantic schema before the UI sees it, so a new edge case fails loudly in one place instead of shipping as a hotfix. Added to the feature you already run.

    Where a person decides: Your team owns the schema; changes are reviewed like any code.

    AI productsQuick win · days to 2 weeks
  4. Streaming so users see progress, not a spinner

    Server-sent events from the FastAPI job API to your React or Next.js front end, with partial results and step names as they happen, so a long job reads as work in progress, not a hang.

    Where a person decides: Your designers decide what the user sees at each step.

    AI productsQuick win · days to 2 weeks
  5. GPU workers that scale to zero

    The worker runs on RunPod serverless: it starts when the queue fills and stops when it empties, with a warm pool sized to your traffic so the first job of the morning is not the slowest.

    Where a person decides: You set the spend ceiling and the warm pool size.

    AI productsStandard build · 2–6 weeks
  6. Retries, timeouts and dead-letter handling

    Jobs that fail at the model or the worker are retried with backoff, capped, then parked in a dead-letter queue with the error, so nothing silently disappears and nothing loops forever.

    Where a person decides: Your on-call engineer owns the dead-letter queue; no failed job is deleted automatically.

    AI productsQuick win · days to 2 weeks

Closest system I’ve shipped: DentaSmile AI. A live three-service SaaS: Next.js, FastAPI and a RunPod GPU worker, ~110 s per job, queued and polled. Built for dental clinics.

SaaS and software companies · Agent prototype rescue

Still demoing an agent that loops on the third run?

  1. Prototype rebuilt with one typed shared state

    The prototype rebuilt as a LangGraph graph with one typed shared state instead of message passing, Pydantic-validated outputs at every agent boundary, a QA agent, and retries with correction capped at two attempts.

    Where a person decides: Outputs that fail QA twice are parked for a person with the reason. Nothing loops or fails silently.

    AI systemsComplex system · multi-week
  2. Provider-agnostic model layer

    Models swappable per agent, Claude, OpenAI, Gemini or an open-weight model, without touching orchestration. The typed state and the QA gate stay the same whichever model runs.

    Where a person decides: Your team chooses models per step and can change them any time.

    AI systemsQuick win · days to 2 weeks
  3. Tool calls made safe and idempotent

    Every tool the agent can call gets a typed input schema, a read-only or write flag, an idempotency key and a budget, so a retried step cannot send twice or charge twice.

    Where a person decides: You set the budget per run; a tool that exceeds it stops the run with the reason.

    AI systemsStandard build · 2–6 weeks
  4. Graph replay tests with recorded runs

    Real runs recorded as fixtures and replayed in pytest with model calls stubbed, checking routing, state transitions and tool calls rather than output quality, so a refactor of the graph fails in CI, not in a demo. Output scoring lives in the eval set.

    Where a person decides: Your team decides which runs become fixtures and when they are refreshed.

    AI systemsQuick win · days to 2 weeks
  5. Human-in-the-loop checkpoints inside the graph

    Named pause points in the LangGraph graph where the run waits for a person: approve, edit the state, or reject with a reason. The run resumes from the checkpoint, not from the start.

    Where a person decides: Your product team decides which steps need a person and who that person is.

    AI systemsStandard build · 2–6 weeks
  6. Run traces your support team can read

    Every agent step logged with inputs, outputs, model, tokens and time, viewable per run in a simple page, so “why did it say that” is a lookup rather than a reproduction.

    Where a person decides: You decide retention and who may open a trace that contains customer data.

    AI systemsQuick win · days to 2 weeks

Closest system I’ve shipped: LeadForge AI. 6 agents, one typed shared state, Pydantic at every boundary, pytest over the graph, QA retries capped at two. Built for lead research.

Still returning free text from uploads and fixing the UI with hotfixes?

  1. Uploads extracted into your schema, then validated

    PDFs, scans and messy uploads extracted by text and vision models into your schema, with deterministic validation after the model: the model proposes, rules decide. Built into your existing app and API.

    Where a person decides: Records that fail the gate are queued for your team or your users to resolve.

    AI systemsComplex system · multi-week
  2. Entity resolution instead of one threshold

    An escalating matcher, exact to fuzzy in tiers, built for OCR noise, so names, references and codes from a scan resolve reliably against the records already in the user’s account.

    Where a person decides: Confidence thresholds are set with you and visible to users where it matters.

    AI systemsStandard build · 2–6 weeks
  3. Upload flow with progress and a review screen

    Drag-and-drop upload in your Next.js app, a queued extraction job with progress, then a side-by-side screen where the user confirms or corrects each field before it is saved.

    Where a person decides: Nothing is saved to the user’s account until they confirm it.

    AI productsStandard build · 2–6 weeks
  4. Corrections fed back into the eval set

    Every field a user corrects is stored with the original document and added to the extraction eval set as a regression case, so accuracy is measured against real corrections rather than a demo set.

    Where a person decides: You decide which customers’ documents may be used and how long they are kept.

    AI systemsQuick win · days to 2 weeks
  5. Tables, handwriting and multi-page documents

    Line-item tables, handwritten fields, stamps and documents that run over several pages handled as their own cases with their own checks, instead of one prompt that works on the clean sample.

    Where a person decides: You bring the ugly real documents; the acceptance set is agreed before the build.

    AI systemsStandard build · 2–6 weeks
  6. Per-customer document layouts mapped once

    A customer’s recurring layout, their supplier’s invoice or their own form, is mapped once and stored per layout, so the second document of that kind extracts with the same checks and no new prompt.

    Where a person decides: A new layout is confirmed by the user before the mapping is saved.

    AI systemsStandard build · 2–6 weeks

Still changing prompts by feel and finding out from the invoice?

    A few hundred real inputs from your product, labelled with your team, scored automatically on each change: exact fields by rules, judgement calls by a model grader you have checked against humans.

    Where a person decides: Your team labels the set; a grader is trusted only after it agrees with them.

    AI systemsQuick win · days to 2 weeks
  2. Prompt and model changes gated in CI

    Every prompt, schema or model change runs the eval set in GitHub Actions or GitLab CI, with the score diff posted on the pull request, so a regression is seen before merge, not after release.

    Where a person decides: Your reviewers decide whether a score drop is acceptable; the gate only reports.

    AI systemsStandard build · 2–6 weeks
  3. Live outputs sampled and scored daily

    A sample of yesterday’s production outputs scored each night against the same eval rules and grader, per model and per tenant, with an alert in Slack when the score drifts below the floor you set.

    Where a person decides: An alert opens a review by your team; nothing is rolled back or switched automatically.

    AI systemsStandard build · 2–6 weeks
  4. Prompt caching and model routing to cut cost

    Stable context cached so it is not paid for on every call, cheap models for easy cases and strong models for hard ones, with the routing rule explicit and the cost per request logged.

    Where a person decides: You set the quality floor from the eval set; cost is cut only above it.

    AI systemsQuick win · days to 2 weeks
  5. Inference cost per tenant, in your database

    Tokens, model, latency and cost written per request and per tenant into your Postgres or SQL Server, with a Power BI or Metabase view, so AI pricing and plan limits rest on numbers.

    Where a person decides: Your finance lead decides the plan limits; the system only measures and alerts.

    Data systemsStandard build · 2–6 weeks
  6. Rate limits, budgets and kill switch per tenant

    Per-tenant request limits, a daily spend ceiling and a switch that turns a feature off for one customer or everyone, enforced in the FastAPI layer, so an abusive script cannot run up the bill overnight.

    Where a person decides: Your on-call engineer holds the switch; limits are set by you per plan.

    AI productsQuick win · days to 2 weeks
